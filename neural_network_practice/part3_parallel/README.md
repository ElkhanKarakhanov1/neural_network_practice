# Задание 3. Параллельная подготовка и аугментация данных

## Назначение проекта

Модуль `part3_parallel` расширяет второе задание: чтение файлов выполняется несколькими потоками, а аугментация изображений — пулом процессов. Также реализованы последовательная версия, сравнение времени и интерактивное меню. Результаты сохраняются в `.npy`, а статистика сравнения — в `performance_report.json`.

## 1. Организация producer-consumer

Паттерн producer-consumer, или «производитель — потребитель», разделяет создание задач и их выполнение. Компоненты взаимодействуют через очереди: производитель помещает задания, а потребители извлекают их по мере готовности. Это позволяет согласовать этапы, работающие с разной скоростью.

В проекте конвейер устроен следующим образом:

```text
Поток-производитель: поиск файлов
                  ↓
queue.Queue: пути к файлам
                  ↓
Несколько потоков-потребителей: чтение и преобразование
                  ↓
queue.Queue: массивы
                  ↓
Основной поток: отправка задач через Pool.apply_async()
                  ↓
Пул процессов: аугментация
                  ↓
Callback → очередь результатов → объединение → .npy
```

Производитель обходит дерево каталогов через `os.walk()` и отбирает файлы по расширению. Потоки-потребители читают CSV или изображения и передают массивы следующему этапу. Основной поток отправляет задания в пул процессов, а callback помещает готовые результаты в очередь завершённых задач.

Очереди путей и загруженных массивов имеют ограниченную ёмкость. Если следующий этап не успевает, предыдущий ожидает освобождения места. Дополнительно ограничено число одновременно отправленных задач в пул. Это создаёт обратное давление и уменьшает накопление промежуточных данных.

Каждый файл получает индекс. Результаты объединяются по этим индексам, а не по времени завершения задач. Поэтому порядок строк или изображений не зависит от того, какой работник завершил работу первым.

## 2. Обеспечение потокобезопасности

Потоки одного процесса имеют общую память, поэтому одновременное изменение общих объектов требует синхронизации. Передача заданий организована через `queue.Queue`, предназначенную для взаимодействия потоков.

Общие счётчики найденных, прочитанных и обработанных файлов изменяются внутри `with lock:`, где `lock` — объект `threading.Lock`. Блокировка не позволяет двум потокам одновременно выполнить защищённый участок. Список ошибок защищается тем же механизмом. Рассчитывать только на GIL для корректности общей логики нельзя.

Callback не изменяет напрямую словарь итоговых массивов, а помещает сообщение в потокобезопасную очередь. Словарь результатов обновляет основной поток. Для каждой аугментации используется отдельный генератор случайных чисел с seed, зависящим от индекса файла. При неизменных входных данных обе версии выполняют одинаковые случайные преобразования.

Межпроцессный обмен выполняет `multiprocessing.Pool`: аргументы и результаты передаются между процессами, а не через общую изменяемую переменную Python. Это упрощает изоляцию задач, но создаёт расходы на сериализацию и передачу массивов.

Для штатного завершения потоков используются специальные сигналы в очередях. После обработки вызываются `join()` для потоков, затем `close()` и `join()` для пула. При исключении или прерывании устанавливается событие остановки, пул завершается через `terminate()`, после чего выполняется ожидание работников. Такое управление ресурсами предусмотрено для обычного завершения и обрабатываемых ошибок; аварийное завершение процесса на уровне ОС может потребовать дополнительного контроля тайм-аутов.

## 3. Почему для аугментации выбраны процессы

Чтение файлов включает ожидание диска, поэтому для этого этапа подходят потоки. Пока один поток ожидает ввод-вывод, другой может работать с другим файлом. Однако чтение и декодирование также содержат вычисления, поэтому разделение на I/O-bound и CPU-bound здесь не абсолютно.

Аугментация выполняет повороты, отражения и добавление шума. Для вычислительно тяжёлых преобразований процессы позволяют использовать несколько ядер независимо от ограничений GIL обычной сборки CPython. Поэтому в задании выбран пул процессов как отдельный вычислительный этап.

Важно учитывать особенность реализации: многие операции NumPy освобождают GIL. Следовательно, данная аугментация не обязательно будет быстрее именно в процессах — потоки тоже могут параллельно выполнять низкоуровневые операции NumPy и не требуют межпроцессного копирования массивов. Выбор процессов соответствует архитектуре задания, а фактическую эффективность нужно подтверждать измерениями.

Для изображений сохраняется оригинал и создаётся заданное число преобразованных копий. CSV не подвергается случайной аугментации: повороты и отражения не имеют смысла для таблицы XOR, а изменение признаков без согласования меток может испортить данные. Признаки CSV нормализуются после объединения; последний целевой столбец не изменяется.

## 4. Потоки, процессы и влияние GIL

GIL (Global Interpreter Lock) — глобальная блокировка интерпретатора. В стандартной сборке CPython с включённым GIL только один поток одного интерпретатора одновременно исполняет Python-байткод. Поэтому добавление потоков обычно не ускоряет тяжёлые циклы, написанные на чистом Python.

Процессы имеют отдельные интерпретаторы и отдельные GIL. Они могут выполнять такие вычисления параллельно на разных ядрах. Выигрыш появляется, когда работа достаточно тяжёлая, задач несколько и затраты на запуск и обмен данными меньше полученной экономии.

| Условия | Предпочтительный подход |
|---|---|
| Ожидание файлов, сети или других внешних ресурсов | Обычно потоки |
| Длительные независимые вычисления на чистом Python | Обычно процессы |
| NumPy и другие библиотеки, освобождающие GIL | Потоки могут быть эффективны; нужны измерения |
| Очень маленькие задачи | Часто последовательная обработка |
| Большие массивы и дорогая передача между процессами | Потоки могут быть выгоднее при безопасном доступе к памяти |

Потоки требуют меньше затрат на запуск и используют общую память. Процессы лучше изолируют состояние, но обычно потребляют больше памяти и требуют передачи данных. Даже процессы не гарантируют ускорения: ограничением могут стать диск, пропускная способность памяти или слишком большое количество работников.

Существуют free-threaded сборки CPython, в которых GIL может быть отключён. Поэтому вывод о невозможности параллельного исполнения Python-байткода относится к сборкам с включённым GIL, а не ко всем вариантам Python.

## 5. Измерение производительности

`performance.py` сравнивает одинаковую обработку в последовательном и параллельном режимах. Измеряется полный цикл: поиск, чтение, аугментация, нормализация и сохранение. Время параллельного варианта включает запуск и завершение пула; сравнение готовых массивов в замер не входит.

По умолчанию выполняются три повтора с чередованием порядка запуска. Для каждого режима вычисляется медиана. Коэффициент ускорения равен `T_sequential / T_parallel`: значение больше единицы означает преимущество параллельной версии, меньше единицы — последовательной.

В отчёт записываются параметры, окружение, времена отдельных запусков и результат проверки равенства массивов. Входные файлы нельзя менять во время эксперимента. Файловый кеш ОС влияет на измерения; чередование порядка не устраняет это влияние полностью. Текущее сравнение оценивает последовательную и гибридную версии, но не заменяет отдельный эксперимент «только потоки против только процессов».

На вашем `dataset.csv` из четырёх строк параллельная версия может оказаться медленнее: объём работы мал, а аугментация CSV не выполняется. Это нормальный результат, но он не позволяет оценить эффективность тяжёлой обработки изображений.

## 6. Структура и запуск

```text
part3_parallel/
├── app/
│   ├── augment.py             # преобразования изображений
│   ├── producer_consumer.py   # параллельный конвейер
│   ├── performance.py         # последовательная версия и сравнение
│   └── main.py                # интерактивное меню
└── README.md
```

Требуются NumPy, Pillow для изображений и модули второго задания. Запуск из корня репозитория:

```bash
python -m part3_parallel.app.main
```

Меню:

```text
1. Последовательная обработка
2. Потоки чтения + пул процессов
3. Сравнить версии и сохранить performance_report.json
0. Выход
```

Для вашего CSV выберите расширение `csv`. В пункте 3 при успешной обработке создаются `sequential.npy`, `parallel.npy` и `performance_report.json`. При настройках по умолчанию они сохраняются в `data/output`. На Windows точка входа защищена условием `if __name__ == "__main__"` и вызывает `freeze_support()`.

## Заключение

Проект использует потоки для этапа чтения и процессы для независимых преобразований. Потокобезопасность обеспечивается очередями, блокировкой общего состояния и сбором результатов в основном потоке. Выбор способа параллелизма зависит от характера нагрузки и расходов на обмен данными, а не только от числа ядер.

Ограничение реализации: готовые массивы накапливаются в RAM перед объединением. Ограниченные очереди не решают проблему памяти итогового набора. Для больших данных потребуется запись результатов частями, например через memory mapping.
